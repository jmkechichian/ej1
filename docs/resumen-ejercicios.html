1. Arquitectura general del proyecto

La solución es un proyecto Maven multi-módulo que separa las tres capas clásicas de una aplicación empresarial y empaqueta todo en un EAR desplegable en WildFly.

MóduloEmpaqueCapa / rol
ej1-apijarInterfaz remota de negocio (contrato compartido con el cliente Java)
ejbejbCapa de Negocio (Stateless) + Capa de Datos (Singleton) + entidad
webwarCapa de Presentación Web: Servlet+JSP y JSF (Ej. 4)
earearEmpaqueta ejb + web; incluye ej1-api.jar en lib/
ej1-consolejarCapa de Presentación como aplicación Java de consola (EJB remoto)

Flujo de una petición

Navegador / Consola
      ↓
Capa Presentación   (Servlet+JSP | JSF | app consola)
      ↓  interfaz LOCAL (web)  /  interfaz REMOTA (consola)
Capa Negocio        @Stateless TrabajadorSaludService   ← valida la regla de negocio
      ↓  interfaz LOCAL
Capa Datos          @Singleton TrabajadorSaludDAO       ← almacena (List en memoria)
Nota sobre la persistencia: en este primer prototipo la capa de datos guarda los registros en una List en memoria dentro del Singleton. No se usa base de datos todavía (el persistence.xml queda inerte porque la entidad es un POJO, no una @Entity JPA). Al reiniciarse el servidor la lista se vacía.

2. Ejercicio 1 — Aplicaciones Jakarta EE y Session Beans

Se pide una aplicación Jakarta EE de tres capas para gestionar una entidad, con: capa de presentación web (Servlet/JSP) y Java de consola; capa de negocio con Stateless Session Beans (interfaces local y remota) que controlen al menos una regla de negocio al dar de alta; y capa de datos con un Singleton Session Bean (interfaces local y remota).

2.1 La entidad TrabajadorSalud

ejb/src/main/java/tse2026/ej1/entidad/TrabajadorSalud.java

Representa a un trabajador de la salud. Cumple la consigna de tener al menos tres atributos de tipos distintos: texto (String), numérico (Long), fecha (LocalDate) y booleano (Boolean).

public class TrabajadorSalud implements Serializable {
    private Long id;              // numérico
    private String nombre;        // texto
    private String apellido;
    private String especialidad;
    private String matricula;     // texto — clave de negocio
    private LocalDate fechaIngreso; // fecha
    private Boolean activo;       // booleano
    // constructor vacío + constructor completo + getters/setters + toString()
}

Por qué implements Serializable: las instancias viajan por la interfaz remota (consola) y se guardan en beans JSF de vista, dos escenarios que exigen que el objeto sea serializable.

2.2 Capa de Acceso a Datos — Singleton Session Bean

ejb/src/main/java/tse2026/ej1/datos/TrabajadorSaludDAO.java (+ ...DAOLocal, ...DAORemote)

Interfaz local

@Local
public interface TrabajadorSaludDAOLocal {
    void agregar(TrabajadorSalud trabajador);
    List<TrabajadorSalud> obtenerTodos();
    TrabajadorSalud buscarPorMatricula(String matricula);
}

Interfaz remota

@Remote
public interface TrabajadorSaludDAORemote {
    void agregar(Long id, String nombre, String apellido, String especialidad,
                 String matricula, String fechaIngreso, Boolean activo);
    String listar();
    String buscarRemotoPorMatricula(String matricula);
}

La interfaz remota trabaja con tipos simples y devuelve texto para que un cliente remoto no dependa de la clase entidad.

Implementación

@Singleton
public class TrabajadorSaludDAO
        implements TrabajadorSaludDAOLocal, TrabajadorSaludDAORemote {

    private List<TrabajadorSalud> trabajadores = new ArrayList<>();

    @Override public void agregar(TrabajadorSalud t) { trabajadores.add(t); }

    @Override public List<TrabajadorSalud> obtenerTodos() { return trabajadores; }

    @Override public TrabajadorSalud buscarPorMatricula(String matricula) {
        for (TrabajadorSalud t : trabajadores)
            if (t.getMatricula().equals(matricula)) return t;
        return null;
    }
    // ... versiones de la interfaz remota que arman/serializan a String
}

Explicación:

  • @Singleton: el contenedor crea una única instancia compartida por toda la aplicación. Es ideal como “almacén” en memoria: todas las capas (web, JSF, consola) ven la misma lista.
  • Por defecto un Singleton tiene concurrencia gestionada por el contenedor con bloqueo de escritura, así que los accesos concurrentes quedan serializados sin código extra.
  • Implementa las dos interfaces (@Local y @Remote), como pide la letra.

2.3 Capa de Negocio — Stateless Session Bean

ejb/src/main/java/tse2026/ej1/negocio/TrabajadorSaludService.java (+ ...ServiceLocal, y ...ServiceRemote en ej1-api)

Implementación (parte local)

@Stateless
public class TrabajadorSaludService
        implements TrabajadorSaludServiceLocal, TrabajadorSaludServiceRemote {

    @EJB
    private TrabajadorSaludDAOLocal dao;   // inyección del Singleton por interfaz local

    @Override
    public void agregar(TrabajadorSalud trabajador) {
        // ===== REGLA DE NEGOCIO =====
        TrabajadorSalud existente = dao.buscarPorMatricula(trabajador.getMatricula());
        if (existente != null) {
            throw new ReglaNegocioException(
                "Ya existe un trabajador con la matrícula " + trabajador.getMatricula());
        }
        dao.agregar(trabajador);
    }

    @Override public List<TrabajadorSalud> obtenerTodos() { return dao.obtenerTodos(); }
    @Override public TrabajadorSalud buscarPorMatricula(String m) { return dao.buscarPorMatricula(m); }
}

La regla de negocio y ReglaNegocioException

ejb/src/main/java/tse2026/ej1/negocio/ReglaNegocioException.java

@ApplicationException(rollback = true)
public class ReglaNegocioException extends RuntimeException {
    public ReglaNegocioException(String mensaje) { super(mensaje); }
}

Por qué una excepción propia con @ApplicationException: cuando un @Stateless lanza una RuntimeException común, el contenedor la envuelve en EJBException y hace rollback. La capa web entonces no puede distinguir “matrícula repetida” de un error real, y responde HTTP 500. Al anotar la excepción con @ApplicationException, el contenedor la deja pasar tal cual hasta la presentación, que la captura y muestra un mensaje claro (HTTP 400 en el Servlet, FacesMessage en JSF).

Explicación de @Stateless

  • El contenedor mantiene un pool de instancias sin estado; cada llamada puede atenderla una instancia distinta. Perfecto para lógica de negocio: escala bien y es simple.
  • Provee interfaz local (usada por la capa web, misma JVM → rápida) y interfaz remota (usada por la consola vía red).
  • Transacción automática: cada método corre en su propia transacción contenedora (CMT).

Interfaz remota (módulo ej1-api)

@Remote
public interface TrabajadorSaludServiceRemote {
    String agregar(Long id, String nombre, String apellido, String especialidad,
                   String matricula, String fechaIngreso, Boolean activo);
    String listar();
    String buscarRemotoPorMatricula(String matricula);
}

Vive en su propio módulo ej1-api para que la aplicación de consola dependa solo de este contrato liviano y no del jar completo de EJBs. El ejb depende de ej1-api con scope compile, de modo que ej1-api.jar viaja dentro del EAR (carpeta lib/) y queda en el classpath del servidor.

2.4 Capa de Presentación Web — Servlet + JSP

web/src/main/java/tse2026/ej1/web/TrabajadorSaludServlet.java • web/src/main/webapp/WEB-INF/trabajadores.jsp

@WebServlet("/trabajadores")
public class TrabajadorSaludServlet extends HttpServlet {

    @EJB
    private TrabajadorSaludServiceLocal service;   // inyección de la capa de negocio (local)

    protected void doGet(...)  { /* accion = listar | buscar */ }
    protected void doPost(...) { /* accion = agregar */ }

    private void agregar(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        try {
            TrabajadorSalud t = new TrabajadorSalud(
                Long.parseLong(req.getParameter("id")),
                req.getParameter("nombre"), req.getParameter("apellido"),
                req.getParameter("especialidad"), req.getParameter("matricula"),
                LocalDate.parse(req.getParameter("fechaIngreso")),
                Boolean.parseBoolean(req.getParameter("activo")));
            service.agregar(t);
            resp.sendRedirect(req.getContextPath() + "/trabajadores?accion=listar");
        } catch (ReglaNegocioException | IllegalArgumentException e) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, e.getMessage());
        }
    }

    private void listar(...)  { req.setAttribute("trabajadores", service.obtenerTodos());
                                req.getRequestDispatcher("/WEB-INF/trabajadores.jsp").forward(req, resp); }
    private void buscar(...)  { /* service.buscarPorMatricula(...) → JSP */ }
}

Explicación:

  • Patrón MVC clásico: el Servlet es el controlador, el JSP la vista, el EJB el modelo/negocio.
  • @EJB TrabajadorSaludServiceLocal: el servlet usa la interfaz local porque corren en la misma JVM (dentro del EAR).
  • El catch combina ReglaNegocioException (regla de negocio) e IllegalArgumentException (dato de formulario inválido, p. ej. id no numérico) y responde HTTP 400 con el mensaje.
  • Tras el alta hace sendRedirect (patrón POST-Redirect-GET) para evitar reenvíos.

2.5 Capa de Presentación — Aplicación de consola

ej1-console/src/main/java/tse2026/ej1/consola/ConsolaApp.java

Properties env = new Properties();
env.put(Context.INITIAL_CONTEXT_FACTORY,
        "org.wildfly.naming.client.WildFlyInitialContextFactory");
env.put(Context.PROVIDER_URL, "remote+http://localhost:8080");
env.put(Context.SECURITY_PRINCIPAL, "prueba");     // usuario de aplicación en WildFly

// ejb:<app>/<módulo>/<bean>!<interfaz remota>

              TrabajadorSaludServiceRemote.class.getName();

        (TrabajadorSaludServiceRemote) ctx.lookup(jndi);

Explicación:

  • La consola es un proceso Java fuera del servidor: obtiene el EJB por JNDI remoto con el esquema ejb:.
  • WildFlyInitialContextFactory + remote+http:// son el mecanismo actual de WildFly para invocación remota de EJB sobre HTTP.
  • Requiere un usuario de aplicación (prueba/prueba, dado de alta con add-user).
  • En ejecución se agrega al classpath JBOSS_HOME/bin/client/jboss-client.jar (script ej1-console/ejecutar-consola.bat).

2.6 Errores detectados y corregidos

El esqueleto tenía varios problemas que impedían compilar o desplegar. Correcciones aplicadas:

#ProblemaCorrección

3La regla de negocio devolvía HTTP 500: el @Stateless envuelve las RuntimeException en EJBException.Nueva ReglaNegocioException con @ApplicationException(rollback=true).
4ConsolaApp usaba JNDI antiguo (http-remoting://) sin InitialContextFactory → NoInitialContextException.WildFlyInitialContextFactory + remote+http:// + credenciales.
5En deployments/ de WildFly convivían el EAR y los módulos sueltos (.war, .jar); el WAR suelto fallaba al no resolver el EJB de otro deployment.Se despliega solo el EAR.

3. Ejercicio 1.2 — Despliegue en WildFly local con Docker

Se empaqueta el servidor + la aplicación en una imagen Docker, a partir de la imagen oficial de WildFly.

Dockerfile

Dockerfile (raíz del proyecto)

FROM quay.io/wildfly/wildfly:41.0.0.Final-jdk21

# 1) Usuario de aplicación para que la consola invoque el EJB remoto
USER root
RUN /opt/jboss/wildfly/bin/add-user.sh -a -u prueba -p prueba --silent

# 2) Desplegar el EAR (el deployment scanner lo toma al arrancar)
COPY ear/target/ej1.ear /opt/jboss/wildfly/standalone/deployments/

# 3) Compatibilidad con PaaS tipo OpenShift (UID aleatorio del grupo 0)
RUN chgrp -R 0 /opt/jboss/wildfly/standalone \
 && chmod -R g+rwX /opt/jboss/wildfly/standalone

USER 1000
EXPOSE 8080 9990
CMD ["/opt/jboss/wildfly/bin/standalone.sh", "-b", "0.0.0.0", "-bmanagement", "0.0.0.0"]

Explicación línea por línea:

  • FROM ...wildfly:41.0.0.Final-jdk21: misma versión que el servidor local.
  • add-user.sh -a: crea el usuario de aplicación prueba dentro de la imagen.
  • COPY ear/target/ej1.ear ...deployments/: el EAR generado por mvn install se copia a la carpeta que WildFly escanea; al arrancar lo despliega solo.
  • chgrp 0 + chmod g+rwX: en OpenShift el contenedor corre con un UID aleatorio que pertenece al grupo 0; los archivos deben ser legibles/escribibles por ese grupo. Sirve tanto local como en la nube.
  • -b 0.0.0.0: WildFly acepta conexiones desde fuera del contenedor.

4. Ejercicio 2 — Despliegue en la Nube (PaaS)

PaaS (Plataforma como Servicio): el proveedor gestiona sistema operativo, runtime y escalado; nosotros solo entregamos la aplicación (aquí, una imagen Docker). Se usó Red Hat OpenShift (Developer Sandbox, gratuito).

Estrategia: build binario dentro del cluster

No hace falta registro de imágenes externo ni Docker local: se sube el contexto (Dockerfile + ej1.ear) y OpenShift construye la imagen con buildah y la publica en su registro interno.

# 1) Autenticación (token del Sandbox)
oc login --token=sha256~... --server=https://api.rm2.thpm.p1.openshiftapps.com:6443

# 2) Definir un build de estrategia docker con entrada binaria
oc new-build --name ej1 --strategy docker --binary

# 3) Subir el contexto y construir en el cluster
oc start-build ej1 --from-dir . --follow

# 4) Crear Deployment + Service desde la imagen construida
oc new-app ej1
oc set resources deploy/ej1 --requests=memory=768Mi --limits=memory=1200Mi

# 5) Publicar una URL HTTPS pública (Route con TLS edge)
oc expose svc/ej1
oc patch route/ej1 -p '{"spec":{"tls":{"termination":"edge"}}}'

Objetos de OpenShift/Kubernetes involucrados:

  • BuildConfig + ImageStream: reciben el contexto y producen/versionan la imagen.
  • Deployment: mantiene el pod con WildFly corriendo (lo reinicia si cae).
  • Service: nombre y IP estable interna hacia el pod (puerto 8080).
  • Route: expone el Service en una URL pública con HTTPS.

5. Ejercicio 4 — Capa de presentación con JSF y AJAX

Se moderniza la capa web con Jakarta Faces (JSF) — implementación Mojarra 4.1 sobre WildFly — conviviendo con la versión Servlet/JSP. Todas las llamadas al servidor son por AJAX (etiqueta <f:ajax>), sin recargar la página.

5.1 Backing bean

web/src/main/java/tse2026/ej1/web/jsf/TrabajadorSaludBean.java

@Named
@RequestScoped
public class TrabajadorSaludBean {

    @EJB
    private TrabajadorSaludServiceLocal service;   // la MISMA capa de negocio del Ej. 1

    // modelo del formulario de alta
    private Long id; private String nombre, apellido, especialidad, matricula;
    private LocalDate fechaIngreso; private boolean activo = true;
    // búsqueda
    private String matriculaBuscar;
    // resultado mostrado en la tabla
    private List<TrabajadorSalud> trabajadores;

    @PostConstruct
    public void init() { trabajadores = service.obtenerTodos(); }

    public void agregar() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        try {
            service.agregar(new TrabajadorSalud(id, nombre, apellido,
                    especialidad, matricula, fechaIngreso, activo));
            ctx.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO,
                    "Trabajador agregado", "Matricula " + matricula));
            limpiarFormulario();
        } catch (ReglaNegocioException e) {
            ctx.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_ERROR,
                    "No se pudo agregar", e.getMessage()));
        }
        trabajadores = service.obtenerTodos();
    }

    public void buscar() {
        if (matriculaBuscar == null || matriculaBuscar.isBlank()) {
            trabajadores = service.obtenerTodos(); return;
        }
        TrabajadorSalud t = service.buscarPorMatricula(matriculaBuscar.trim());
        trabajadores = (t == null) ? List.of() : List.of(t);
    }

    public void listarTodos() { matriculaBuscar = null; trabajadores = service.obtenerTodos(); }
    // getters / setters
}

Explicación:

  • @Named: expone el bean a las páginas con el nombre EL #{trabajadorSaludBean}.
  • @RequestScoped: el estado real vive en el Singleton de la capa de datos, no en el bean. El bean solo coordina cada petición; en cada llamada AJAX se recrea, @PostConstruct recarga la lista y el método de acción la ajusta. Así se evita cualquier problema de serialización/pasivación.
  • @EJB TrabajadorSaludServiceLocal: reutiliza sin cambios la capa de negocio del Ejercicio 1 (misma regla de negocio, misma validación).
  • La ReglaNegocioException se traduce a un FacesMessage de error visible en pantalla.

Cómo funciona el AJAX (criterios de usabilidad):

  • <f:ajax execute="@form">: al pulsar el botón se envían por AJAX solo los campos del formulario.
  • render="@form :msgs :resultado": el servidor devuelve solo esos fragmentos de HTML y JSF los reemplaza en la página — sin recarga completa.
  • event="keyup" delay="300": búsqueda en vivo mientras se escribe, con 300 ms de espera para no saturar el servidor.
  • required="true" + <h:messages>: validación del lado servidor con mensajes inmediatos.
  • <f:convertDateTime type="localDate">: convierte el texto yyyy-MM-dd del input HTML5 type="date" a LocalDate.

6. Cómo ejecutar todo

Compilar y probar

cd ej1
mvn clean install          # 7 módulos + 3 tests unitarios → BUILD SUCCESS

A) WildFly local (standalone)

& "$JBOSS_HOME/bin/standalone.bat"
"$JBOSS_HOME/bin/jboss-cli.bat" --connect --command="deploy .../ear/target/ej1.ear --force"
#  Web JSP : http://localhost:8080/ej1-web/trabajadores
#  Web JSF : http://localhost:8080/ej1-web/trabajadores.xhtml
#  Consola : ej1-console/ejecutar-consola.bat

B) WildFly en Docker (Ej. 1.2)

docker compose up -d --build
#  http://localhost:8080/ej1-web/trabajadores.xhtml
docker compose down        # detener

C) OpenShift / PaaS (Ej. 2)

oc login --token=... --server=...
bash openshift/desplegar.sh
#  https://ej1-<usuario>-dev.<cluster>.openshiftapps.com/ej1-web/trabajadores
Aviso: el contenedor Docker y el WildFly standalone usan los mismos puertos 8080/9990; ejecutar solo uno a la vez.
